# The guard: what a goal run may do

**Why a guard plugin**: the engine hides from a plugin the calls its own timers and buttons cause, so the runner can't see its own timer-started runs. The guard plugin identifies runs by `$.agent.list()` `spawnedBy` plus the description. It sets `run_scope`, applies the goal guard (`guard_check`), refuses the person-only tools (`decide_item`, `cancel_run`, ...) to agents and the model, and keeps run reports out of the chat.

## Tool maps and decisions (`core/src/guard.ts`, MCP `guard_check`)

Called by the guard plugin for each run's tool calls. `tool_map` maps tool-name patterns to categories. It denies `off` categories, and `propose` categories unless an approved proposal for that category is still being carried out (active, not completed): an approval covers its whole action however many calls it takes, until the run completes the item. Every decision is recorded in `goal_tool_calls`. Outside goal runs it allows everything.

**Command rules**: `Bash(git push*)` / `PowerShell(...)` matches a shell call when any simple command in it (`commandParts`: split at `&&`, `;`, `|`, `$(`..., leading `VAR=x` dropped) matches the glob, case-insensitively, and wins over a rule on the tool's name; without input none matches, so `standingAllowRules` never allows plain `Bash` for one. The GitHub fixer templates use them (`githubRules` in `hooks/templates.ts`): push and `gh pr create` are `code.pull_request`, other gh writes, `gh api` and `gh auth` are `github.write` (off). Name matching only, like the data rule.

The Issue Fixer asks at `/goal-new` whether to wait for the `refined` label (`ISSUE_FIX_WAIT`, first, and the default for `watches('')`) or start on every new issue (`ISSUE_FIX_EVERY`); the answer picks its intake text (`ISSUE_FIX_REFINED_INTAKE` / `ISSUE_FIX_INTAKE`, before the shared `ISSUE_FIX_WORK`) and its issue watches. Waiting, one watch, "refined issues" (`refinedWatch`), lists open issues carrying the label whoever opened them: **the label is the trust signal**, since only someone with triage rights can label an issue, so an outsider can't label their own to get it built. It builds from the refinement comment (a trusted author's, so `ISSUE_READ` keeps it) and treats the body as background, since the reporter can still edit it. Not waiting, its watches split issues by `author_association` (`issueWatch`, `TRUSTED_ASSOCIATIONS`): collaborators' issue numbers under "new issues", anyone else's as `<number> by <login>` under "new issues from others", which the run asks about (`ask_person`) before reading. Existing Issue Fixers keep the split until the person swaps their watches (`update_goal`). Its "comments on its pull requests" watch (`prCommentWatch`) lists only trusted authors' comments and reviews on its open `issue-fix/` PRs as `<number> <id>`; a run acts on one through a proposed push and can't reply on GitHub (`github.write` off), so questions come to the person.

The Issue Refiner (`refineRules`, `refineWatch`, `ISSUE_REFINE`) turns an issue into a spec the person approves, posted as a comment with `refined` (or, for facts only the reporter has, questions with `needs-clarification`). Its one propose category, `github.issue`, covers `gh issue comment*`, `gh issue edit*` and `gh label create*`; a glob can't tell `--add-label` from `--body`, so its instructions forbid changing an issue's title or body. Its label rules are named one by one (`gh label delete*`/`edit*`/`clone*` off) instead of `gh label*`, so `gh label list` stays unmapped: allowed, and it doesn't mark the first run, and the memory it writes, as having read outside text. `gh issue view*` is `untrusted`; pushing, pull requests and the other writes are off. It settles every decision with the person (`ask_person`, one per question, with the issue's link) before proposing, and reads only code, in a clone of its own. Its issue watches split by author like the fixer's and leave out issues labelled `refined`, `needs-clarification` or `help wanted` (its instructions scope that skip to those two watches, since a reply comes on a `needs-clarification` issue); the reply watch is in the watches rule.

A new Issue Refiner asks at `/goal-new` which issues to refine: only those labelled `needs-refinement` (`REFINE_WAIT`, first, and the default for `watches('')`) or every new issue (`REFINE_EVERY`, the split by author above). Waiting, its two new-issue watches become one (`needsRefinementWatch`: open issues with `needs-refinement`, not `refined` or `needs-clarification`, whoever opened them, since the label is the person's go-ahead), its intake is `REFINE_PICKED_INTAKE` before the shared `ISSUE_REFINE_WORK`, and a Ready proposal also removes `needs-refinement`. Existing refiners keep their watches until the person swaps them.

The Issue Triage goal (`triageRules`, `triageWatch`, `ISSUE_TRIAGE`) comes before the refiner: its watch lists open issues without `triaged`, from anyone (triage is how outside issues get sorted; it only ever adds labels the person approved and runs no code). It proposes one `github.label` item per run covering every new issue (kind and priority from the repo's own labels, a likely duplicate, `triaged`); `gh issue edit*` and `gh label create*` are `github.label`, `gh issue view*` and `gh issue list*` (titles, for duplicates) are `untrusted`, `gh label list` is unmapped, and commenting, closing, pushing, pull requests and the other writes are off. Then it asks one question, "Which of these should be refined?", as an `ask_person` item **that carries an action** (category `github.schedule`): the answer approves that action (`addItem` keeps `asks_person` with the action; `decideItem` `answer` approves it like a proposal, so the item stays active and the guard lets the category through until the run completes it). `github.schedule` is the rule `gh issue edit * --add-label needs-refinement` (`SCHEDULE_COMMAND`), longer than `gh issue edit*`, so the answer approves adding that one label and nothing else: any other `gh issue edit` falls to `github.label`. A `*` matches anything, flags included, so a still longer rule, `gh issue edit *-* --add-label needs-refinement` (`SCHEDULE_WITH_FLAGS`), sends any command with a flag before the label (`--body x`, `--remove-label`, a second `--add-label`, `-R`) back to `github.label`: issue numbers have no `-`.

The PR Reviewer (`reviewRules`, `pullWatch`) has one GitHub write: `gh api repos/*/pulls/*/reviews*` is `github.review` (propose), and wins over `gh api*` by length; pushing, `gh pr create`/`merge`/`review` and the other writes are off, and `gh pr view`/`diff`/`checkout` are `untrusted`. Its instructions keep the review event COMMENT (the JSON goes in a file, which the guard can't see). `commandParts` splits at `{`/`}`, so `gh api repos/{owner}/{repo}/...` leaves `gh api repos/` and falls to `gh api*`: the run must write the repo out, from `git remote get-url origin` (`gh repo*` is off, `gh repo view` included). Its watches list non-draft PRs as `<number>@<head sha>` (each push re-triggers), splitting by `author_association` like the issue watches: anyone else's PR (`<number>@<sha> by <login>`) is asked about before it is read or tested, since testing runs its code. It and the Issue Fixer act on each other's work (a posted review starts a fixer run, an approved push a re-review), which the runaway breaker doesn't count, so `PR_REREVIEW` posts re-reviews only for real problems and asks the person after `PR_REVIEW_ROUNDS` (3) posted reviews on one PR; every hop also needs an approval.

## "allow" only means Quarterdeck doesn't object

The guard plugin turns a deny into a refusal and otherwise passes the call on (`next(e)`), so Claude Code's own permission rules (allow rules, auto mode, a prompt) decide every call it doesn't refuse, `auto` and approved ones included. The plugin never answers allow (the plugin directory won't list one that does). Docs and UI copy must not say `auto` lets a call through; the pane's "Claude Code allow rules" (`goal_detail`) lists the allow rules a goal's `auto` tools need.

## Untrusted content

A tool that reads outside text marks the run (`goal_runs.untrusted_at` / `untrusted_source`, `markRunUntrusted`: the first source is kept, except that a mark inherited from a run summary gives way to any outside read, and `watch events` to any other outside read), and from then on its `auto` categories act as `propose` in both `guardRun` and `addItem` (an auto `add_item` becomes a proposal, `untrusted` in the result), so injected text can't take an action nobody approved.

- Readers are `BUILTIN_UNTRUSTED` (WebFetch, WebSearch, the browsers, Gmail's get/search/download tools) plus any tool a goal maps to the reserved category `untrusted` (`UNTRUSTED_CATEGORY`: always allowed, never an action category, left out of the web autonomy list).
- A brief that hands out watch events marks the run too (`run.untrusted` in the brief, source `WATCH_EVENTS_SOURCE`); a status set by a run marked only by them gets no ⚠ on the goal's line, and the expanded card says "set … after reading watch events" (`watchEvents` in `toStatusNote`, `hooks/model.ts`), since every watch-started run reads them.
- The guard sees names, and a shell call's command, so `Bash` (curl, `gh issue view`) and `Read` of a download mark nothing unless mapped to `untrusted` (`Bash(gh issue view*)`).
- Memory a marked run writes (`remember`) carries the mark (`goal_memory.untrusted_source`), and a brief that hands it out marks its run (`memory <id> (written after …)`, `untrusted: true` on the entry), so injected text can't wait one run to skip the guard; memory left out of the brief marks nothing, and its `memory_index` entry carries no text (`{ id, kind, untrusted: true }`), so no outside text reaches an unmarked run; `recall` of it marks the run with the same source, and so does a curation run's brief, which hands out every memory. The person's own memory, feedback and answers are never marked.
- So is a run summary (#42's test case: a planted request reaching the next run only through a summary). A brief whose `recent_runs` (the last `RECENT_RUNS`, 3) include a run that read outside content itself (`readOutsideContent`: marked, and not only by a summary) marks its run (`run summary <id> (written after …)`), and flags every marked run's entry `untrusted: true`. A mark inherited from a summary doesn't pass on, so it ends 3 runs after the last outside read instead of marking every later run for good; the gap left is an instruction restated by marked runs, which can't act on it. Chosen by the person, 17 Nov 2026, over fully transitive marks.
- Memory curation (`core/src/curation.ts`) can't launder injected text into trusted memory: the run only proposes (`propose_curation`), the server applies exactly what the person approved, an untrusted memory can't be merged with or replace a trusted one, and what is merged from one keeps the mark (approving doesn't trust it). Its brief is marked by untrusted memory and by the summary of any run in its brief (every one since the last curation, up to 60) that read outside content, and memory a marked curation run adds, merges or rewords carries the run's mark, the person's own included (the request's notes say so). Unlike a summary's, a memory's mark lasts until the person Trusts it, so a "So far" fold of a tainted summary keeps marking the runs that read it.
- The person clears a mark with Trust (pane, MCP `trust_memory`, person-only) or on the web page (PATCH `trusted: true`, or rewriting the text).

## Quarterdeck's own data

A run's `Bash`/`PowerShell` command naming `.quarterdeck`/`.conductor`, `tasks.db` or `QUARTERDECK_DB`/`CONDUCTOR_DB` (or a custom `QUARTERDECK_DB` path), and a file tool's path inside those folders or at the database, are refused first in `guardRun`, whatever the tool map says (`touchesQuarterdeckData`, category `quarterdeck-data`, recorded). The guard plugin sends only `command`, `file_path`, `notebook_path`, `path` and `pattern` as `guard_check`'s `input` (`callInput`); an older server drops the key. It matches names, so a script in another file gets past it: roadmap 1.37 (sandbox) closes that. A goal whose `working_dir` is inside `~/.quarterdeck` can't use file tools on its own folder.

# The guard: what a goal run may do

**Why a guard plugin**: the engine hides from a plugin the calls its own timers and buttons cause, so the runner can't see its own timer-started runs. The guard plugin identifies runs by `$.agent.list()` `spawnedBy` plus the description. It sets `run_scope`, applies the goal guard (`guard_check`), refuses the person-only tools (`decide_item`, `cancel_run`, ...) to agents and the model, and keeps run reports out of the chat.

**A run's hand-back starts no turn** (#114): Claude Code delivers a finished background subagent's report to the main loop as a prompt with origin `{ kind: 'peer', from: <agent id>, handback: true, ... }` (seen in Claude Code 2.1.3xx transcripts; `session.receive` is never raised for it, so the guard's older hook there never caught one). The guard's `prompt.submit` hook answers `{ drop }` when that agent id (`origin.from`, else the `<agent-message from="…">` frame) is a run by `runIdFor` (`spawnedBy`), so the standing session no longer pays a turn over its whole history per run. Only `peer` prompts are looked at: the person's own text naming a run agent goes on. `SubagentHandback` itself still runs, so Claude Code counts the report delivered.

## Tool maps and decisions (`core/src/guard.ts`, MCP `guard_check`)

Called by the guard plugin for each run's tool calls. `tool_map` maps tool-name patterns to categories. It denies `off` categories, and `propose` categories unless an approved proposal for that category is still being carried out (active, not completed): an approval covers its whole action however many calls it takes, until the run completes the item. Every decision is recorded in `goal_tool_calls`. Outside goal runs it allows everything.

**Command rules**: `Bash(git push*)` / `PowerShell(...)` matches a shell call when any simple command in it (`commandParts`: split at `&&`, `;`, `|`, `$(`..., leading `VAR=x` dropped, and a word wholly in one pair of quotes with no whitespace or quote inside unwrapped, so `--add-label "needs-refinement"` matches like the bare word, #94) matches the glob, case-insensitively, and wins over a rule on the tool's name; without input none matches, so `standingAllowRules` never allows plain `Bash` for one. The GitHub fixer templates use them (`githubRules` in `hooks/templates.ts`): push and `gh pr create` are `code.pull_request`, other gh writes, `gh api` and `gh auth` are `github.write` (off). Name matching only, like the data rule.

The Issue Fixer asks at `/goal-new` whether to wait for the `refined` label (`ISSUE_FIX_WAIT`, first, and the default for `watches('')`) or start on every new issue (`ISSUE_FIX_EVERY`); the answer picks its intake text (`ISSUE_FIX_REFINED_INTAKE` / `ISSUE_FIX_INTAKE`, before the shared `ISSUE_FIX_WORK`) and its issue watches. Waiting, one watch, "refined issues" (`refinedWatch`), lists open issues carrying the label whoever opened them: **the label is the trust signal**, since only someone with triage rights can label an issue, so an outsider can't label their own to get it built. It builds from the refinement comment (a trusted author's, so `ISSUE_READ` keeps it) and treats the body as background, since the reporter can still edit it. Not waiting, its watches split issues by `author_association` (`issueWatch`, `TRUSTED_ASSOCIATIONS`): collaborators' issue numbers under "new issues", anyone else's as `<number> by <login>` under "new issues from others", which the run asks about (`ask_person`) before reading. Existing Issue Fixers keep the split until the person swaps their watches (`update_goal`). Its "comments on its pull requests" watch (`prCommentWatch`) lists only trusted authors' comments and reviews on its open `issue-fix/` PRs as `<number> <id>`, leaving out the PR Reviewer's clean reviews by their wording (`cleanReview`), which ask for nothing but would each cost a full run; a run acts on one through a proposed push and can't reply on GitHub (`github.write` off), so questions come to the person. It reads a review's inline comments with the server tool `pr_inline_comments` (`PR_INLINE_TOOL`, `untrusted`, so calling it marks the run; it is in the guard's `GUARDED_QUARTERDECK`, so a goal whose tool map doesn't name it is refused), not a `gh api .../comments` command (#68): a glob's `*` matches any flag and there is no negation, so no rule could allow the read's `--jq` and refuse every write flag (rules naming `-X`, `-f` and the like missed a clustered `-iX POST`). The tool runs one fixed `gh api repos/<owner>/<name>/pulls/<n>/comments --paginate`, keeps only trusted authors' comments and returns `{id, path, line, author, body}` (`mcp/src/tools/pr_inline_comments.ts`). With no rule for the read, every `gh api` call the Issue Fixer makes falls to `gh api*`, `github.write`. A forge whose read a glob can hold may still set `rules.inlineRead`/`inlineWrites` (`inlineReadRules`); GitHub sets neither. Existing Issue Fixers keep the old read and rules until `update_goal` gives them the template's. After a push that answers inline comments it resolves their threads with the server tool `resolve_review_thread` (`RESOLVE_THREAD_TOOL`, `code.pull_request`, so approving the push covers it; it is in the guard's `GUARDED_QUARTERDECK`). It is a tool and not a `gh api graphql` rule because `commandParts` splits at `(` and `{`, so a rule sees only `gh api graphql -f query='mutation` and would let any mutation through, a merge included. The tool sends one fixed mutation, only for threads on an open PR that a trusted author started (`mcp/src/tools/resolve_review_thread.ts`; it and `pr_inline_comments` share `TRUSTED` in `mcp/src/tools/trusted.ts`, which must match `TRUSTED_ASSOCIATIONS`, as a core test checks), posts nothing, and records `review_threads_resolved`.

The Issue Refiner (`refineRules`, `refineWatch`, `ISSUE_REFINE`) turns an issue into a spec the person approves, posted as a comment with `refined` (or, for facts only the reporter has, questions with `needs-clarification`). Its one propose category, `github.issue`, covers `gh issue comment*`, `gh issue edit*` and `gh label create*`; a glob can't tell `--add-label` from `--body`, so its instructions forbid changing an issue's title or body. Its label rules are named one by one (`gh label delete*`/`edit*`/`clone*` off) instead of `gh label*`, so `gh label list` stays unmapped: allowed, and it doesn't mark the first run, and the memory it writes, as having read outside text. `gh issue view*` is `untrusted`; pushing, pull requests and the other writes are off. It settles every decision with the person (`ask_person`, one per question, with the issue's link) before proposing, and reads only code, in a clone of its own. Its issue watches split by author like the fixer's and leave out issues labelled `refined`, `needs-clarification` or `help wanted` (its instructions scope that skip to those two watches, since a reply comes on a `needs-clarification` issue); the reply watch is in the watches rule.

A new Issue Refiner asks at `/goal-new` which issues to refine: only those labelled `needs-refinement` (`REFINE_WAIT`, first, and the default for `watches('')`) or every new issue (`REFINE_EVERY`, the split by author above). Waiting, its two new-issue watches become one (`needsRefinementWatch`: open issues with `needs-refinement`, not `refined` or `needs-clarification`, whoever opened them, since the label is the person's go-ahead), its intake is `REFINE_PICKED_INTAKE` before the shared `ISSUE_REFINE_WORK`, and a Ready proposal also removes `needs-refinement`. Existing refiners keep their watches until the person swaps them.

The Issue Triage goal (`triageRules`, `triageWatch`, `ISSUE_TRIAGE`) comes before the refiner: its watch lists open issues without `triaged`, from anyone (triage is how outside issues get sorted; it only ever adds labels the person approved and runs no code). It proposes one `github.label` item per run covering every new issue (kind and priority from the repo's own labels, a likely duplicate, `triaged`); `gh issue edit*` and `gh label create*` are `github.label`, `gh issue view*` and `gh issue list*` (titles, for duplicates) are `untrusted`, `gh label list` is unmapped, and commenting, closing, pushing, pull requests and the other writes are off. Then it asks one question, "Which of these should be refined?", as an `ask_person` item **that carries an action** (category `github.schedule`): the answer approves that action (`addItem` keeps `asks_person` with the action; `decideItem` `answer` approves it like a proposal, so the item stays active and the guard lets the category through until the run completes it). `github.schedule` is the rule `gh issue edit * --add-label needs-refinement` (`SCHEDULE_COMMAND`), longer than `gh issue edit*`, so the answer approves adding that one label and nothing else: any other `gh issue edit` falls to `github.label`. A `*` matches anything, flags included, so a still longer rule, `gh issue edit *-* --add-label needs-refinement` (`SCHEDULE_WITH_FLAGS`), sends any command with a flag before the label (`--body x`, `--remove-label`, a second `--add-label`, `-R`) back to `github.label`: issue numbers have no `-`.

The PR Reviewer (`reviewRules`, `pullWatch`) has one GitHub write: `gh api repos/*/pulls/*/reviews*` is `github.review` (propose), and wins over `gh api*` by length; pushing, `gh pr create`/`merge`/`review` and the other writes are off, and `gh pr view`/`diff`/`checkout` and `gh issue view` are `untrusted`. It also reads each issue a PR closes (`closingIssuesReferences`) with `ISSUE_READ`, so only trusted authors' comments reach it, and reviews the PR against what the issue asks; questions for the reviewer go in the review summary, never on the issue. Its instructions keep the review event COMMENT (the JSON goes in a file, which the guard can't see). `commandParts` splits at `{`/`}`, so `gh api repos/{owner}/{repo}/...` leaves `gh api repos/` and falls to `gh api*`: the run must write the repo out, from `git remote get-url origin` (`gh repo*` is off, `gh repo view` included). Its watches list non-draft PRs as `<number>@<head sha>` (each push re-triggers), splitting by `author_association` like the issue watches: anyone else's PR (`<number>@<sha> by <login>`) is asked about before it is read or tested, since testing runs its code. It and the Issue Fixer act on each other's work (a posted review starts a fixer run, an approved push a re-review), which the runaway breaker doesn't count, so `PR_REREVIEW` raises only real problems on a re-review (a clean one is still posted, as "Reviewed at <sha>: no problems found" with no inline comments, so the PR doesn't look unreviewed) and asks the person after `PR_REVIEW_ROUNDS` (3) posted reviews that raise something on one PR; every hop also needs an approval.

## "allow" only means Quarterdeck doesn't object

The guard plugin turns a deny into a refusal and otherwise passes the call on (`next(e)`), so Claude Code's own permission rules (allow rules, auto mode, a prompt) decide every call it doesn't refuse, `auto` and approved ones included. The plugin never answers allow (the plugin directory won't list one that does). Docs and UI copy must not say `auto` lets a call through; the pane's "Claude Code allow rules" (`goal_detail`) lists the allow rules a goal's `auto` tools need.

## Untrusted content

A tool that reads outside text marks the run (`goal_runs.untrusted_at` / `untrusted_source`, `markRunUntrusted`: the first source is kept, except that a mark inherited from a run summary gives way to any outside read, and `watch events` to any other outside read), and from then on its `auto` categories act as `propose` in both `guardRun` and `addItem` (an auto `add_item` becomes a proposal, `untrusted` in the result), so injected text can't take an action nobody approved.

- Readers are `BUILTIN_UNTRUSTED` (WebFetch, WebSearch, the browsers, Gmail's get/search/download tools) plus any tool a goal maps to the reserved category `untrusted` (`UNTRUSTED_CATEGORY`: always allowed, never an action category, left out of the web autonomy list).
- A brief that hands out watch events marks the run too (`run.untrusted` in the brief, source `WATCH_EVENTS_SOURCE`); a status set by a run marked only by them gets no ⚠ on the goal's line, and the expanded card says "set … after reading watch events" (`watchEvents` in `toStatusNote`, `hooks/model.ts`), since every watch-started run reads them.
- The guard sees names, and a shell call's command, so `Bash` (curl, `gh issue view`) and `Read` of a download mark nothing unless mapped to `untrusted` (`Bash(gh issue view*)`).
- How the source is worded (`untrustedLabel`, #52): a call matched by a command rule names the rule, `<tool>: <pattern without the trailing *>` (`Bash: gh issue view` for `Bash(gh issue view*)`); a name-only rule and the built-in readers give the tool name. The original read is kept in its own column, `untrusted_root`, on `goal_runs` and `goal_memory` (set with the source under the same first-source-kept rule; `remember` copies it with the source; Trust clears both), so a mark inherited from memory reads `memory <id> (first: <root>)`: one level deep however many runs pass it on. A run-summary mark carries the summarized run's root too. Rows from before the column fall back to their source text, keeping its old nesting.
- Memory a marked run writes (`remember`) carries the mark (`goal_memory.untrusted_source`), and a brief that hands it out marks its run (`memory <id> (first: …)`, `untrusted: true` on the entry), so injected text can't wait one run to skip the guard; memory left out of the brief marks nothing, and its `memory_index` entry carries no text (`{ id, kind, untrusted: true }`), so no outside text reaches an unmarked run; `recall` of it marks the run with the same source, and so does a curation run's brief, which hands out every memory. The person's own memory, feedback and answers are never marked.
- So is a run summary (#42's test case: a planted request reaching the next run only through a summary). A brief whose `recent_runs` (the last `RECENT_RUNS`, 3) include a run that read outside content itself (`readOutsideContent`: marked, and not only by a summary) marks its run (`run summary <id> (written after …)`), and flags every marked run's entry `untrusted: true`. A mark inherited from a summary doesn't pass on, so it ends 3 runs after the last outside read instead of marking every later run for good; the gap left is an instruction restated by marked runs, which can't act on it. Chosen by the person, 17 Nov 2026, over fully transitive marks.
- Memory curation (`core/src/curation.ts`) can't launder injected text into trusted memory: the run only proposes (`propose_curation`), the server applies exactly what the person approved, an untrusted memory can't be merged with or replace a trusted one, and what is merged from one keeps the mark (approving doesn't trust it). Its brief is marked by untrusted memory and by the summary of any run in its brief (every one since the last curation, up to 60) that read outside content, and memory a marked curation run adds, merges or rewords carries the run's mark, the person's own included (the request's notes say so). Unlike a summary's, a memory's mark lasts until the person Trusts it, so a "So far" fold of a tainted summary keeps marking the runs that read it.
- **Hidden text is shown, not passed on** (#172, `cleanOutsideText()` in `core/src/outside-text.ts`). Outside text can carry instructions a person never sees, so the readers Quarterdeck controls replace HTML comments (an unterminated one runs to the end), invisible and text-direction characters, and tag characters (U+E0000 to U+E007F) with visible markers (`[hidden comment removed]`, `[3 invisible characters removed]`) and count them. It runs on `pr_inline_comments` bodies, each watch line in the brief, and every field of the server tool `issue_read` (an issue's title, body and trusted authors' comments, or the one comment asked for; `untrusted` and in `GUARDED_QUARTERDECK` like `pr_inline_comments`). `cleanStatusNote` uses it without markers. A `gh issue view` command's output can't be cleaned, so the Issue Refiner, Issue Fixer and PR Reviewer templates read issues with `issue_read` (`GITHUB.issueRead`, `ISSUE_READ_TOOL` mapped `untrusted` in their tool maps). The command's rules stay `untrusted`: goals made before this keep using it until `update_goal` gives them the template's instructions and tool map, and the refiner's reply read (`refiner.replyRead`) stays a command, since a reporter's reply is a comment `issue_read` leaves out.
- The person clears a mark with Trust (pane, MCP `trust_memory`, person-only) or on the web page (PATCH `trusted: true`, or rewriting the text).

### Allowed after outside content (#159)

A goal's `auto_after_outside` list (`goals.auto_after_outside`, JSON array, schema 24) names `auto` categories the person keeps `auto` in a marked run; `propose` and `off` are unaffected. Only the person sets it: `update_goal` from their own session (refused from a run, like every `update_goal`), or the web goal page (a checkbox beside an `auto` category, PATCH `auto_after_outside`); the pane's goal_detail lists it ("auto, even after reading outside text", `autoAfterOutsideText`). Turning it on for a category whose tool rules push code, create or merge a PR, or are broad (a whole tool, `Bash`/`Edit`/`Write`, a whole MCP server: `isRiskyToolRule`, `autoAfterOutsideWarning` in `core/src/goal-changes.ts`) warns, naming the rules, and still saves when confirmed: a planted instruction could then push code or open a PR without review. Goals that write code, like the Issue Fixer, should keep the default.
- A listed category's call goes through only via the guard plugin's `guarded_run` tool. It takes the command and the full contents of every file the command needs, checks them (a 64 KB size limit, then rules for known token formats, private-key blocks and the run's environment values of 8+ characters, then a one-shot Haiku check with a 15-second timeout), and on a pass the server (`guarded_stage`) writes the files under `~/.quarterdeck/guarded/<run>/`, points the command at those copies and records a one-use check (command and file hashes). **`guarded_run` never runs anything**: the run makes the returned call itself, so Claude Code's permission rules still decide it. `guardRun` lets the call through only when it exactly matches an unused check whose files still match; the same call made directly, a changed command or file, or a reused check falls back to `propose`. A size or rule hit refuses without calling Haiku; a refusal, a wrong-format answer or no answer refuses with the reason.
- **The Haiku check treats the payload as data** (#170, `modelCheck()`, `guardedSystem()`, `guardedPrompt()` in the guard plugin's `hooks/register.ts`). The payload is written by a run that may be following planted instructions, so it can't be allowed to speak to the checker. Each call makes a random nonce (6 bytes, hex) and puts the command and each file in its own `<payload-<nonce> kind="command">` / `kind="file" path="…"` block. A fake closing tag in a file can't end its block, because the file was written before the nonce existed. The system prompt holds what the payload can't touch: the goal's name, its job (the objective plus the instructions clipped to 1,000 characters, `GUARDED_JOB_CHARS`, returned by `stageGuardedCall()`'s dry run) and the category. It says everything inside the tags is data, that an instruction there aimed at the checker is itself a reason to refuse, and that the call must do this goal's job and carry no secrets. Only a first line of exactly `VERDICT: ALLOW` passes. `VERDICT: REFUSE: <reason>` refuses with the reason (clipped to 200 characters). Anything else, a bare "YES" included, refuses with "the model check gave an answer in the wrong format". The run's target (repo, PR) joins the context once #168 gives the guard one.
- A marked run holding the setting is refused reads of secret locations (`~/.ssh`, `~/.aws`, `~/.npmrc`, `~/.config/gh`, `.env*`, the data folder) and `env`, `printenv`, `gh auth token`, PowerShell's `env:` drive, recorded under the `secrets` category.
- Before the mark, those reads are allowed but recorded on the run (#169): `goal_runs.secrets_read_at`, `secrets_read_source` (what `touchesSecrets()` matched, first one kept) and `secrets_read_paths` (JSON array of the files read: a file tool's path, or the `.env` files a shell command names, from `secretFilePaths()`), through `markRunSecretsRead()`. Only goals with a non-empty `auto_after_outside` record them. In such a run the setting stops applying (`afterOutsideApplies()`): the guard's staged-call branch, `stageGuardedCall()` and `addItem()` all fall back to propose, with `secretsReadReason()` naming the read. `stageGuardedCall()` also checks the payload against the values in each file read (`secretFileValues()`: `KEY=VALUE` values and other lines of `ENV_VALUE_MIN_CHARS` or more), naming the file. The run record says so: the overview's runs carry `secrets_read` (the source, or null), which `goal_detail` and the pane's last-run line show as "read secrets (<source>), so allowed-after-outside was off" (`secretsReadText()` in `hooks/model.ts`), and the web run page shows the same from `secrets_read_at`/`secrets_read_source`.
- The tool call is recorded with the reason `AFTER_OUTSIDE_NOTE` and the item with `state.after_outside` (`AFTER_OUTSIDE_ITEM_NOTE`): it went through after outside content because the person allowed it.
- The checks lower the risk of disclosure but don't remove it: encoded text can get past them. Say so wherever the setting is offered; it fits private repos better than public ones.

## Quarterdeck's own data

A run's `Bash`/`PowerShell` command naming `.quarterdeck`/`.conductor`, `tasks.db` or `QUARTERDECK_DB`/`CONDUCTOR_DB` (or a custom `QUARTERDECK_DB` path), and a file tool's path inside those folders or at the database, are refused first in `guardRun`, whatever the tool map says (`touchesQuarterdeckData`, category `quarterdeck-data`, recorded). The guard plugin sends only `command`, `file_path`, `notebook_path`, `path` and `pattern` as `guard_check`'s `input` (`callInput`); an older server drops the key. It matches names, so a script in another file gets past it: roadmap 1.37 (sandbox) closes that. A goal whose `working_dir` is inside `~/.quarterdeck` can't use file tools on its own folder.
